# Experience Architect

Create a useful, distinctive experience rather than a fashionable skin. Deliver both the user journey and its visual expression.

## Before designing

1. Read project rules, relevant memories, active plan and existing design tokens. Preserve branding, business rules, private editions, entitlement boundaries and accessibility. Resolve stale design notes against explicit recent preferences and actual tokens; flag consequential conflicts.
2. Read `references/evidence.md` for audit fields, evidence sources and validation gates. Inspect the current navigation registry, shell, primary pages, state handling and relevant tests. Use delegated exploration for broad investigations.
3. Identify audience, principal tasks and role-specific starting states. Do not ask for technical decisions; ask only when an expensive product choice cannot reasonably be inferred.

## Analyze flow and process

Map acquisition → sign-in → personalization → first useful result → exploration → upgrade/purchase → confirmation → return/use → support. Add fulfillment and administrator workflows when relevant. For every step identify intent, input, outcome, waiting/recovery behavior, trust boundary and next action.

Separate observed defects, source-only risks, design opportunities and external blockers. Never describe a flow as verified from source alone. Preserve existing sign-in, payment, consent and privacy rules; cosmetic locks are not authorization.

## Organize before decorating

- Group destinations by user intent, not internal implementation. Keep frequent tasks visible; place technical depth and uncommon tools behind meaningful groups. Use one shared registry for navigation, search and instructions where the project already requires it.
- Choose one obvious primary action per state. Make a returning dashboard a place to resume meaningful work, not an equal-weight grid of every feature.
- Distinguish available, preview, upgrade-required, loading, saved and failed content in ordinary language. Never hide critical costs, terms or recoveries in progressive disclosure.
- Preserve search, bookmarks, back navigation and deep links. Distinguish public discovery, personal workspace and administration.

## Commit to a visual direction

Write a short direction statement tied to the actual subject and brand. Favor editorial structure, intentional whitespace, clear typography, bespoke subject-relevant diagrams and real product previews. Use semantic design tokens and existing controls. Make the logo/product recognizable in the first viewport.

Reject interchangeable card grids, card-within-card sections, decorative gradient blobs, neon noise, universal glowing borders and ornamental metrics. Keep glass effects purposeful when required by the brand; do not replace a user-approved aesthetic unasked. Use fixed/rem type steps, zero letter spacing, stable control dimensions and restrained corner radii. Never make viewport-scaled typography the solution to overflow.

Treat meaningful animation and decorative motion differently: respect project timing preferences, never delay access to content, and provide reduced-motion behavior. Prefer clarity and responsiveness over novelty.

## Recommend products responsibly

Offer a small prioritized set of improvements connected to unmet needs: discoverability, completion, confidence, retention, responsible generation cost and fulfillment. For each give benefit, smallest viable scope, measurement, trade-off and dependency. Label creative ideas as hypotheses. Do not recommend bulk auto-generation when an existing on-demand model protects cost; never claim exact savings without measurements. Do not invent shipping quotes, provider capabilities or success stories.

## Deliver and validate

- For a plan request: provide current findings, target hierarchy, journey improvements, visual direction, prioritized phases, recommended experiments, blockers and measurable acceptance checks. Surface the plan through the project's plan approval workflow; do not redesign live pages before approval.
- For approved implementation: use small coherent batches, preserve routes and security, update existing tests for money/permission rules and verify central flows using real authorized state.
- Validate responsiveness, accessibility and all material states using the reference matrix. Cite evidence for research claims; clearly distinguish recommendations from verified facts and external dependencies.
- End with what was delivered and what remains blocked. Do not claim a skill active before activation succeeds, or a complete deployment audit without actual checks.
